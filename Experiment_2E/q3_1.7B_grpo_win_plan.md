# Qwen3-1.7B DeepMath GRPO Hidden-Dynamics Plan

**目标：**在 2 张 H800 上对 `Qwen/Qwen3-1.7B` 进行一轮可审计的全参数 GRPO，先验证 held-out 数学能力是否改善，再使用冻结 checkpoint 和固定 rollout 分析 H1-H9、V1-V9 及 V4 weighted companion 的训练期变化。

**核心原则：**训练、行为评估和 hidden extraction 三阶段解耦。训练期间不请求 `output_hidden_states`；所有 hidden 图均来自相同 held-out 题、相同 rollout slots 和冻结 checkpoint，SwanLab 的 hidden 区只上传 correct-vs-wrong + AUROC 图。

---

## 1. 研究问题与结论边界

本实验依次回答：

1. `Qwen3-1.7B + DeepMath + GRPO` 是否提升未参与训练的数学题表现；
2. 若能力提升，横向 H1-H9 和纵向 V1-V9 是否随训练出现稳定、阶段相关的变化；
3. 这些变化是否在 correct/wrong rollout 间产生稳定分离，而不只是 response length、policy entropy、trajectory-point count 或难度变化的重写；
4. V4 的 median turning 与幅度加权 companion 是否方向一致。

训练 reward 上升只能作为 telemetry。RL 有效性的主判据是冻结 held-out 集上的 `pass@1` 相对 base 改善，`pass@4/pass@8`、格式、长度和截断为辅助结果。单 seed 的 hidden 曲线只能称为 discovery，不直接构成因果机制或 reward-shaping 证据。

---

## 2. 冻结模型、数据和划分

### 2.1 模型

- 模型：`Qwen/Qwen3-1.7B`，不是 `Qwen/Qwen3-1.7B-Base`；
- 固定 `enable_thinking=True`；
- 保存模型 revision、tokenizer revision、chat template、resolved generation config 和 SHA256；
- 数学 prompt 固定要求逐步推理，并将最终答案写入 `\boxed{}`；
- 训练、calibration 和 held-out evaluation 使用同一 tokenizer 与答案 verifier。

### 2.2 DeepMath 候选池

- 原始数据：DeepMath-103K；
- calibration 前保留 level 3-9 及 topic 元数据；
- 正式训练只使用 calibration 后冻结的连续难度带，初始重点比较 `level 3-6` 与 `level 4-6`；
- 不能因为训练 reward 或 hidden 结果不理想而事后修改难度范围；
- 训练集、calibration 集、held-out 256 题按标准化题面 hash 去重，交集必须为 0；
- held-out 集按 difficulty 和 topic 分层，永久不进入训练或 group-filter 候选池。

### 2.3 固定分析单位

- 训练单位：一个 prompt 及其完整 roll8 group；
- 行为评估单位：question；
- correct/wrong hidden 比较：先在同一道 question 内比较，再 question-equal 汇总；
- bootstrap：以 question 为重采样单位，不能把同题的 8 条 rollout 当成 8 个独立问题。

## 3. Phase A：难度与长度 Calibration

### 3.1 样本和生成

从 level 3-9 分层抽取约 512 道 calibration 题，每题固定 roll8，不更新模型参数。生成上限先使用 `12288`，同时审核候选 cap `4096/8192/12288`。

记录：

- answer correctness、`pass@1`；
- `boxed_rate`、parse rate、format correctness；
- response tokens mean/P50/P90/P95；
- natural stop 与各候选 cap 下的 truncation；
- 每个 level 的 `k_correct` 分布，`k_correct in [0,8]`；
- all-wrong、all-correct、mixed correctness 和 useful mixed；
- 每个 difficulty/topic 的 verifier failure。

定义：

\[
\text{mixed-correctness}=\mathbf 1(1\le k_{correct}\le 7),
\]

\[
\text{useful-mixed}=\mathbf 1(2\le k_{correct}\le 6).
\]

### 3.2 难度冻结规则

优先选择满足下列条件的连续难度带：

\[
0.15\le \operatorname{pass@1}\le 0.60,
\]

\[
\text{raw mixed-correctness}\ge 0.35,
\qquad
\text{truncation}\le 0.05.
\]

若多个连续难度带均通过，依次按以下规则选择：

1. useful-mixed 更高；
2. all-wrong 更低；
3. topic 覆盖更广；
4. 在仍相同的情况下选择题数更多的难度带。

若所有难度带的 raw mixed-correctness 均低于 `0.25`，本实验 NO-GO；不能依赖 group filtering 硬救明显失配的难度。

### 3.3 Response cap 冻结

冻结满足以下条件的最小候选值：

- non-format truncation `<=5%`；
- 正确率相对 `12288` 没有超出 question-bootstrap 不确定性的下降；
- parse/boxed rate 没有明显下降。

预计冻结 `8192`，但正式值只能由 calibration 决定。训练、所有 checkpoint evaluation 和所有对照必须共享同一 cap。

## 4. Phase B：20-step 系统与优化 Smoke

从同一个初始模型重新开始，运行 20 个 outer steps。smoke 权重永久排除出正式实验。

GO 条件：

- 无 OOM、NaN、Inf、Ray/vLLM worker crash 或 verifier 崩溃；
- 2 张 H800 均参与训练，FSDP2 shard 正常；
- 每 outer step 实际得到 32 个 accepted groups；
- 每 outer step 为 256 responses，并发生 4 个 optimizer mini-batches；
- group 内 advantage 均值接近 0，有效 group 的 advantage std 非 0；
- reference KL 稳定变化，grad norm、clip fraction、policy entropy 无爆炸；
- filtering acceptance rate 足以在预期时间内形成 batch；
- checkpoint 保存和恢复各验证一次。

如果显存不足，依次调整：

1. 下调 vLLM `gpu_memory_utilization`；
2. 下调每 GPU dynamic token budget；
3. 保持逻辑 batch 不变，通过更小 micro-batch/gradient accumulation 完成；
4. 最后才启用统一的 optimizer CPU offload。

不能通过降低 `train_batch_size`、`rollout.n` 或 `ppo_mini_batch_size` 的逻辑口径来临时绕过 OOM。

## 5. Phase C：正式 GRPO 配置

| 项目 | 冻结值/规则 |
|---|---:|
| 模型 | `Qwen/Qwen3-1.7B`，`enable_thinking=True` |
| 训练方式 | 全参数 GRPO，FSDP2，2×H800 |
| DeepMath 范围 | Phase A 后冻结，候选为 level 3-6 / 4-6 |
| 正式训练规模 | `9,600` accepted groups |
| outer steps | `300` |
| `train_batch_size` | `32 prompts/groups` |
| `rollout.n` | `8` |
| responses / outer step | `32 × 8 = 256` |
| `ppo_mini_batch_size` | `8 prompts = 64 responses` |
| optimizer mini-batches / step | `4` |
| `ppo_epochs` | `1` |
| micro batch | 每 GPU 1 条长 response；dynamic token batching |
| actor learning rate | `1e-6` |
| optimizer | AdamW，`beta1=0.9`、`beta2=0.95`、weight decay `0.01` |
| warmup | 前 `5%` outer steps，即约 15 steps |
| LR schedule | warmup 后 cosine decay 到训练结束 |
| clip ratio | `0.2` |
| KL loss | `use_kl_loss=True`、`coef=1e-4`、`low_var_kl` |
| KL in reward | `False` |
| entropy coefficient | `0` |
| advantage | 每题完整 roll8 内减均值并除标准差 |
| loss aggregation | `token-mean` |
| max prompt length | `2048` |
| max response length | Phase A 从 `4096/8192/12288` 冻结 |
| sampling | temperature `0.8`、top-p `0.95`、top-k `20` |
| rollout tensor parallel | `1` |
| vLLM GPU utilization | smoke 从 `0.55-0.60` 冻结 |
| gradient checkpointing | 开启 |
| remove padding | 开启 |
| CPU offload | 默认关闭，只有 smoke 证明必要时统一开启 |

### 5.1 Batch 语义审计

配置文件和日志必须同时记录 prompt 与 response 两种口径：

\[
32\ \text{prompts}\times8=256\ \text{responses/outer step},
\]

\[
8\ \text{prompts}\times8=64\ \text{responses/mini-batch},
\]

\[
256/64=4\ \text{optimizer mini-batches/outer step}.
\]

当前 veRL 版本必须通过运行时计数确认 `ppo_mini_batch_size` 是 prompt 口径还是已经乘过 `rollout.n`，不能只根据字段名推断。

### 5.2 Reward 与 advantage

主 reward 使用可验证答案正确性：

\[
r_i\in\{0,1\}.
\]

format correctness、boxed rate 和 parse status 独立记录，不默认加入 reward。只有 calibration 显示格式率不足且在正式冻结前决定，才允许加入不超过 `0.1` 的弱格式项；一旦冻结，整个正式 run 不再修改。

对于题目 q 的完整 roll8：

\[
A_{q,i}=\frac{r_{q,i}-\bar r_q}{s_q+\epsilon}.
\]

必须上传 raw reward std、normalized advantage std 和 zero-advantage fraction，以验证 group filtering 与 advantage normalization 均按预期运行。

### 5.3 Dynamic group filtering

正式训练按 answer correctness 保留：

\[
1\le k_{correct}\le7.
\]

规则：

- 保留一个 group 时必须保留该题完整的 8 条 rollout；
- 不从 group 内只挑 correct/wrong response；
- rejected all-correct/all-wrong group 不参与梯度，也不计入 9,600 accepted groups；
- 使用新的 prompt 继续补足 32 个 accepted groups，不对同一道题反复生成直到 mixed；
- 记录 raw prompts、accepted prompts、rejected all-wrong/all-correct、acceptance rate 和补采轮数；
- `2<=k<=6` 只作为 useful-mixed 诊断，不作为额外硬过滤；
- 如果滚动 20 steps 的 acceptance rate 低于 `0.25`，触发预注册的暂停审计，不得静默改变难度或过滤规则。

### 5.4 Checkpoint

保存：

```text
base, 25, 50, 75, 100, 125, 150,
175, 200, 225, 250, 275, 300
```

每个 checkpoint 保存 actor、optimizer、scheduler、global step、resolved config、代码 commit、数据 manifest hash 和 RNG 状态。不能根据训练 reward 峰值提前把某个 checkpoint 变成主结果；final 为预先指定主报告点，中间最佳点只作描述性结果。

## 6. Phase D：固定 Held-out 行为评估

对全部 13 个 checkpoint 使用同一批 256 道 held-out DeepMath 题，每题固定 roll8：

\[
13\times256\times8=26,624\ \text{rollouts}.
\]

所有 checkpoint 共用 question order、rollout-slot seed、sampling config、response cap 和 verifier。

每个 checkpoint 计算：

- empirical `pass@1`；
- 无偏 `pass@4` 和 `pass@8`；
- answer reward、format/boxed/parse rate；
- response length mean/P50/P90；
- truncation；
- policy/token entropy；
- held-out all-wrong/all-correct/mixed/useful-mixed；
- difficulty/topic 分层结果。

若一题的 8 条 rollout 中有 c 条正确：

\[
\operatorname{pass@k}
=1-\frac{\binom{8-c}{k}}{\binom{8}{k}},
\qquad k\in\{1,4,8\}.
\]

以 question 做 4,000 次 bootstrap，报告每个 checkpoint 相对 base 的 pass@k 差和 95% CI。只有 held-out 行为改善，后续 hidden 变化才可以解释为“伴随有效 RL 的内部动力学变化”。

## 7. Phase E：Checkpoint-only Hidden Extraction

### 7.1 输入与存储

- 直接复用 Phase D 已生成的固定 rollout，不重新为 hidden 分析采样；
- response-only token hidden；
- window `128`、stride `32`；
- chunk representation：`chunkMean` 与 `chunkLast`；
- response stages：B1 `0-25%`、B2 `25-50%`、B3 `50-75%`、B4 `75-100%`；
- 横向 primary anchors：`L3`、`L12`、`Lfinal(=L28)`；
- 纵向使用全部 decoder hidden states；
- 每条 rollout 处理后立即归约为 scalar，不永久保存完整 token×layer hidden tensor；
- raw scalar 写 Parquet，并保存 schema、coverage、exclusion count 和输入 hash。

`L24` 不进入本轮预注册的三层主面板，避免把 layer 维度重新扩成四档；若当前 extractor 默认产出 L24，可保留原始 scalar 但不上传主 SwanLab 面板、不参与主检验。

### 7.2 冻结 9+9 指标

指标公式直接继承当前 `experiment_2e/metrics.py` 和 `experiment_2e/reduction.py`，不得根据本轮曲线修改。


### 7.3 Stage reducer 的适用性

SwanLab 的 `stageMean/stageMedian/stageP90` 表示：在某条 rollout 的某个 stage 内，对有效的 stage-local atomic values 进行外层聚合。它不改变 atomic metric 的公式。

以下指标天然支持该维度：H1、H3、H4、H8，以及 V1、V2、V3、V4、V4C、V6、V7。纵向指标先按每个 chunk 计算全层 scalar，再在 stage 内做 mean/median/P90。

H2、H5、H6、H7、H9、V5、V8、V9 是 path、weighted、spectral 或 polynomial 等结构性 stage scalar，使用各自当前 frozen/native 定义。它们不得为了填满三个 reducer 面板而重复上传同一张图，也不得临时改造成 rolling-window 新指标。对应图使用 `stageNative` 命名。

这条规则优先于“每个笛卡尔积面板机械放满 19 张图”，避免重复图和指标定义漂移。

## 8. Correct/Wrong 与 AUROC 计算

对每个：

```text
checkpoint × family × representation × anchor/allLayers × stage × reducer
```

生成 rollout-level scalar。随后：

1. 每道题内分别计算 correct rollout mean 和 wrong rollout mean；
2. 再跨题 question-equal 平均，得到蓝线与红线；
3. 只在同时存在 correct 与 wrong rollout 的题上计算 within-question AUROC；
4. AUROC 方向保持原 metric 方向，同时另存 `best_auc=max(AUC,1-AUC)` 仅供诊断；
5. 以 question 做 4,000 次 bootstrap，保存 correct/wrong 差、AUROC 和 95% CI；
6. 同时保存有效 question 数、correct/wrong rollout 数、coverage 和 exclusion rate。

不能把所有 checkpoint rollout 混合后计算一个 pooled AUROC，也不能让 rollout 较多的题获得更高权重。

## 9. SwanLab 组织与命名

### 9.1 训练 telemetry

训练过程仍上传必要的低成本 scalars，用于确认实验正常：

```text
train/reward/*
train/groups/*
train/optimization/*
train/generation/*
system/*
```

至少包括 reward、answer/format rate、k_correct 分布、all-wrong/all-correct、raw mixed、useful mixed、filter acceptance、zero-advantage、KL、policy entropy、grad norm、clip fraction、LR、length、truncation、step time、tokens/s 和 GPU memory。

hidden 面板不上传独立 scalar 曲线、热图、相关矩阵或额外图片，只上传下述 correct-vs-wrong + AUROC 图。原始 scalar 永久保存为 Parquet。

### 9.2 图形统一格式

每张 hidden 图固定为四个子图：

- B1/B2/B3/B4；
- 横轴：`training_progress = checkpoint_step / 300`；
- 蓝线：question-equal correct mean；
- 红线：question-equal wrong mean；
- 灰色虚线：question-equal within-question AUROC；
- 左轴：metric value；右轴：AUROC；
- 标题注明 family、metric、representation、layer/allLayers、reducer 和 final AUROC；
- 所有图使用相同 checkpoint 横坐标；同一 metric 的不同配置尽量共享 y-axis 范围。

### 9.3 横向 chunk 几何面板

适用于 H1-H7、H9：

```text
hidden_horizontal/
  chunkMean/L3/stageMedian/
  chunkMean/L12/stageMedian/
  chunkMean/Lfinal/stageMedian/
  chunkLast/L3/stageMedian/
  ...
```

对支持外层 reducer 的 family，再提供 `stageMean` 与 `stageP90`。结构性 family 只放在 `stageNative`。

图名示例：

```text
H1_movement__chunkMean_L12_stageMedian
H5_centered_ERV__chunkMean_L12_stageNative
H9_trajectory_ED__chunkLast_Lfinal_stageNative
```

### 9.4 H8 token entropy 面板

H8 不依赖 `chunkMean/chunkLast`，单独组织：

```text
hidden_H8_token/
  L3/stageMean/
  L3/stageMedian/
  L3/stageP90/
  L12/...
  Lfinal/...
```

图名示例：

```text
H8_timeDiffEntropy__token_L12_stageMedian
```

不得在 chunkMean 和 chunkLast 下重复上传完全相同的 H8 图。

### 9.5 纵向 all-layer 面板

V1-V9 与 V4C 不依赖单一横向 anchor，统一使用 `allLayers`：

```text
hidden_vertical/
  chunkMean/allLayers/stageMedian/
  chunkMean/allLayers/stageMean/
  chunkMean/allLayers/stageP90/
  chunkMean/allLayers/stageNative/
  chunkLast/allLayers/...
```

图名示例：

```text
V4_layerUpdateTurning__chunkMean_allLayers_stageMedian
V4C_weightedTurning__chunkMean_allLayers_stageMedian
V8_layerUpdateER__chunkLast_allLayers_stageNative
```

V4C 必须紧邻 V4 primary，并额外生成一张 V4 median 与 V4C weighted 的并排审计图；该并排图仍只含 correct/wrong 和 AUROC，不引入其他图形类型。

### 9.6 默认展示优先级

SwanLab 默认展开：

```text
chunkMean + L3/L12/Lfinal + stageMedian
chunkMean + allLayers + stageMedian
H8 token + L3/L12/Lfinal + stageMedian
```

`chunkLast`、`stageMean`、`stageP90` 和 `stageNative` 作为后续折叠分组。这样默认视图优先显示更稳健的 chunk-mean/median 结果，同时所有预注册配置仍可追溯。

## 10. 统计控制与报告

### 10.1 Training-progress family

对每个预注册 primary scalar 拟合：

```text
metric ~ training_progress + stage + correctness
       + log1p(response_length) + policy_entropy
       + trajectory_point_count + difficulty + topic
       + (1 | question_id)
```

H1-H9/V1-V9 的主 family 做 BH-FDR；V4C 单独标记为 companion，不加入或替换 V4 primary family。报告 effect size、CI、q value、coverage 和跨 checkpoint 曲线。

### 10.2 Outcome-conditioned family

比较：

```text
baseline = length + policy_entropy + trajectory_point_count + difficulty + topic
extended = baseline + hidden metric
```

报告 grouped OOF AUC、增量 AUC、question-equal within-question AUC 和 pair-weighted sensitivity。仅有蓝红线分离而没有超越廉价 baseline 的增量，不能称为可用于 RL shaping 的内部质量信号。

### 10.3 解释限制

- checkpoint 变化不等于 hidden 指标具有因果作用；
- correct/wrong AUC 不等于指标能改进训练；
- final checkpoint 不提升时，hidden 曲线仍可作为 policy-dynamics diagnostic，但不能包装为“伴随能力提升”；
- stage/layer/reducer 不得依据结果事后挑选为唯一主结果；
- 本轮是单 seed discovery，至少需要独立 seed 或独立模型复现后才能形成强结论。

## 11. 资源估算与停止规则

正式时间必须用 Phase B 实测的 tokens/s 和 filtering acceptance rate 重算。粗略预算：

- calibration：2-5 小时；
- 20-step smoke：1-3 小时；
- 300-step GRPO：约 15-30 小时；
- 13 checkpoint × 256 × roll8 行为生成：约 6-14 小时；
- 9+9 hidden extraction、bootstrap 和绘图：约 8-20 小时。

停止并审计的条件：

- 连续出现 OOM/NaN/worker crash；
- filtering acceptance 滚动 20 steps 低于 `0.25`；
- truncation 持续超过 calibration 冻结上限；
- verifier/parse failure 系统性增加；
- checkpoint 无法恢复；
- KL、grad norm、entropy 或 response length 出现明显崩塌。

停止后保留全部 raw rollout、日志和已完成 checkpoint，不静默修改配置续跑成同一个 run。

## 13. 执行顺序

```text
环境/版本审计
-> DeepMath 去重与 calibration manifest
-> level/cap calibration
-> 冻结难度、cap、reward、filtering 与 resolved config
-> 20-step 双卡 smoke
-> 丢弃 smoke 权重
-> 正式 300-step GRPO
-> 固定 13 checkpoint held-out roll8
-> 行为审计与 pass@k
-> checkpoint-only hidden extraction
-> correct/wrong + AUROC 分析
-> SwanLab 分组上传
-> final audit
```

只有前一步审计通过才进入下一步；hidden extraction 不得反向影响 checkpoint、难度带、stage、layer、reducer 或指标定义。
